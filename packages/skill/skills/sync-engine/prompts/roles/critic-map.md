## Compiler review context

<!-- input?: review-context -->

Continue under that pass and frozen-row context. The delegated prompt file is your one
bootstrap read; after it, make no tool calls, inspect nothing else, and return one report.

Read the brief's needs yourself. Rule on every concept row with exactly one verdict:

- `accept`: name its sole authority and lifecycle, judge the concrete second application,
  and state the strongest split considered plus the invariant that defeats it;
- `split`: name each resulting mechanism, lifecycle, and sole authority, plus the
  obligation the split creates; or
- `merge with <row>`: name the shared lifecycle and authority and why neither owns a
  decision the other lacks.

Only `catalog-unchanged` settles genericity: accept it only when this product needs the
catalog card's complete listed action and query surface, then mark its second application
`catalog-settled`. Review `catalog-adapted` rows normally. Reject a concrete subject unless the mechanism is that value's format.
Feature cohesion, interaction, a shared invariant, and desired atomicity do not justify
combining.

Every cross-concept consequence must have an obligation ID and complete closure fields.
Rule on every need placement as well as every concept row. A need may belong to a
concept, composition, host, implementation, or evidence. HTTP projection is normally
host work, physical durability and restart are implementation/evidence work, and
cross-concept policy and repair are composition work. Never demand a concept merely to
avoid a missing owner. Use `reassign` when the candidate chose the wrong layer.

After the row and placement verdicts, report spread authority and missing or incomplete
obligations. Never return the clean sentinel. Use only these forms:

```text
- ROW `design/decomposition.md` — Concept — accept|split|merge with Concept — judgment and required evidence.
- PLACEMENT `N1` — accept|reassign to concept Concept|composition|host|implementation|evidence — judgment.
- AUTHORITY — decision — rows or layers claiming it and required owner.
- OBLIGATION — consequence — missing ID or closure field.
```
